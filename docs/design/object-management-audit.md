# MEM-03：对象管理与资源持有审计

2026-11-06。用户要求全面分析小型软件的200MB级占用。结论基于源码持有链、真实QML对象树和Windows原生资源变化；**本轮增加显式隔离诊断，不实施UI惰性化/渲染替换，不把草案预算当合理占用结论**。当前验证事实见PROGRESS。

关联NFR-01～08、P-01/02/03/05/08/10/12/13/22。沿[新增能力标准](new-capability-standard.md)补齐本轮接口/生命周期/错误/测试；基础专项设计见[MEM-02](client-memory-specialist.md)。schema10、HTTP JSON v1、业务功能不变，没有新服务器、RPC、运行时依赖或后台遥测。

## 一、问题不是“用了C++就该是多少”，要查谁持有了什么

原先提出的220MiB私有提交/190MiB私有工作集只是初稿方向，现已暂停采用。没有证明必要常驻对象及图形底座之前，不应把200MB级目标当作可接受的答案。

必须分开四类：

1. 业务事实/活动会话必须持有的数据。
2. 未打开、已关闭或当前形态根本不用，却仍被强持有的QML对象。
3. 对象数已稳定，但窗口/图形资源、字体、JS堆、分配器高水位仍保留。
4. 真正随重复操作持续增加的对象、句柄或资源。

本轮实际看到了2和3；十次相同设置窗口循环没有出现可达对象数持续增加，不能因此说长期绝无泄漏，也不能把全部高占用都叫泄漏。

## 二、采样边界与框架成本对照

诊断入口：`daymark --object-audit-report <新的JSON路径>`。强制QTemporaryDir资料，通过TaskService预先创建20条今天任务，拒绝同时使用用户data-dir/更新handoff/截图。显式进入验证分支，正常启动不采样、不建立诊断定时器。日志也隔离到临时目录。已有报告拒绝覆盖。

记录：启动稳定10秒、设置/账号/独立日历首次开关、设置重复十次、主窗隐藏/恢复、球/Panel切换、仅球、全部隐藏。另有单次明确标注的`collectGarbage`诊断实验，用于判断关闭后状态，不是生产回收策略。报告不含对象地址、标题、任务内容、账号、URL、私有路径。

对象遍历使用engine rootObjects、窗口、workspace/controller的QObject children和visual childItems并去重。**这是可达对象清点，不是全部分配的堆账本**：不含全部无QObject parent的C++成员/unique_ptr对象、JS/V4内部对象、QSG节点、驱动内存；这些另做静态持有审查。视觉候选只判断item/window的可见性，不代表实际绘制，未排除裁剪/透明。子树统计相互嵌套，不能相加。

Windows统计私有提交、私有/全工作集、OS峰值、句柄，并用VirtualQuery分离已提交的private/mapped/image区域；后者不是分配调用栈，也不能简单相加等同PrivateUsage。GPU专用/共享显存仍未测。采样器的临时集合与报告也占内存，未主观扣除。

### 框架空场景

同一Qt6.10.2/MinGW13.1 Release，本机Windows D3D11、DPR1.5。独立程序各运行15秒，末5秒采样中位数：

| 空场景 | 私有提交 | 全工作集 |
|---|---:|---:|
| 一个1120×720空QQuickWindow | 58.32 MiB | 67.07 MiB |
| 主窗＋340×360空透明工具窗 | 89.20 MiB | 86.77 MiB |

它没有QML engine、Controls、字体策略、业务/账号/工具内容，不是同功能产品，**不能用差值直接计算可省字节**。但已经反证“Qt Quick双窗就必需200～300MB”的判断。只做了一次，不称最终性能分布。

原始诊断源码位于忽略的build/mem02-probe/floor.cpp，原始数据build/mem03-empty-one.json/two.json；应用对象诊断已进入版本化源码。归档证据仅含无隐私元数据/计数和相对时间，见docs/evidence/object-management-audit.json。

## 四、开关窗口后的保留：对象少增，资源大增

同一次预建资料原生流程中的检查点，单位为私有提交：

| 检查点 | 可达对象 | 私有提交 | 关闭后 |
|---|---:|---:|---|
| 初始主窗＋小窗 | 30,029 | 约298 MiB | — |
| 首次打开设置 | 30,086 | 约367 MiB | 隐藏后约367，场景图仍初始化 |
| 首次打开账号 | 30,086 | 约434 MiB | 隐藏后仍约434 |
| 首次打开独立日历 | 30,086 | 约496 MiB | 隐藏后仍约496 |
| 设置第十次关闭 | 30,086 | 约495 MiB | 对象数无持续增加 |
| 球/Panel返回后 | 约29,595 | 约501 MiB | 图形资源继续保留 |
| 一次诊断GC后 | 约29,595 | 约501 MiB | 没有显著提交回落 |

首个工具开关仅新增约57个可达对象，提交却增加约69MiB；随后对象数相同也能再增加60MiB级资源。**不能仅靠计数QObject或给new/delete加管理器解决全部内存。** 首次使用后，三个工具窗口均隐藏且`sceneGraphInitialized=true`，默认persistentGraphics/SceneGraph为true。

反复重开同一设置窗口时数量稳定、私有提交约1MiB级变化，支持“首次开窗资源保留”这一解释；不证明全部60MiB都是驱动/GPU，字体、场景图缓存、私有堆仍需分配栈/图形工具归因。短期阶段数据不当长期稳定平台。

主窗恢复时对象略减，部分委托被回收/重建；这也说明对象数和私有提交不是线性关系。仅球和全部隐藏仍为29,595个可达对象/约500.52MiB私有提交，窗口仍受强持有；最终快照单独归档，不用“主窗仍显示时的球”冒充仅球测试。初次原型在UI加载后逐个创建任务、混合DPR，数值更高；保留在build，不与预建资料正式快照混算。

## 五、所有权与生命周期审查矩阵

| 模块/对象 | 当前持有链与释放时机 | 判断 | 应有的管理边界 |
|---|---|---|---|
| AppRuntime与QML engine | 单一组合根；成员RAII。engine先于workspace/同步/控件控制器销毁 | 退出释放顺序基本合理，不是多engine重复创建 | 保留单engine；把“活到进程退出”和“活到本次使用结束”分开 |
| Main.qml的工具/弹层 | 主窗强持有设置、账号、独立日历、提醒和大量Dialog | 启动即建；close多为hide | 未使用的低频内容不创建；注册/注销时绑定WindowStateStore/命令 |
| 设置四类页 | 一个设置窗内四个内容同时创建，只切visible | 非选中页也持有控件/绑定 | 当前页Loader；按页保存少量状态，不保留整树 |
| DateField/CalendarPicker | 每字段都直接持有fallback Popup及日历；inlineMode时也有回退内容 | 32字段/39日历实例，选择器尚未用即常驻 | 字段只保存值；至少把fallback内容惰性化；最终每宿主共享一个活跃日期/时间选择器 |
| TaskTimingFields/Details | 多个隐藏编辑/新建组件分别持有完整控件 | 会话状态和呈现树混在一起 | 活动会话一个可视编辑子树；草稿在会话中，未编辑时不建重控件 |
| TaskRow菜单 | 每行一个DS.Menu，内含13类动作及子菜单 | 与行数相乘；行本应轻量 | 每宿主一个按taskId/version请求的菜单；共享逻辑定义，打开时建视觉项 |
| CalendarPanel | 两套面板、月历/弹层，隐藏时仍有refreshIndependent/refreshUnscheduled路径 | 不只是对象多，还有隐藏投影 | 可见/使用订阅驱动范围投影；已有日/周年Loader、连续月历复用继续保留 |
| 小窗三形态 | 同一QQuickWindow稳定画布，Panel/Mini/Ball内容均持有 | 防闪烁是有意设计；1699对象不是最大来源 | 先瘦身内容，保持原生画布/呈现栅栏；不为省小量对象回退逐帧缩窗 |
| Shape/Glyph/品牌 | 每个实例自有离屏源，4x/8x；隐藏对象仍存在 | 数量与绘制批处理风险已确认，真实纹理字节未测 | 对照直接矢量/共享图像缓存，按物理尺寸/颜色/DPR失效；保留质量及平台回退 |
| TaskWorkspace快照/模型 | 一份m_cache，四个TaskListModel值成员，索引只存行号 | Task为1296字节固定结构；20条×约四套仅约101KiB固定结构量级，不含堆/投影，不能解释300MiB | 大资料继续共享只读快照＋ID投影；不要为了少量任务重做数据库 |
| 工作线程/服务/数据库 | 值成员QThread；TaskWorker移入线程；finished→deleteLater。退出先排空命令，再quit/wait；服务unique_ptr在load中依次reset | 原始指针m_worker有明确释放关系，不因raw pointer就判泄漏 | 保留线程归属；查取消/晚回调/队列高水位，不能在GUI线程直接删SQL对象 |
| 业务定时器 | workspace/widget等多数为无parent的C++值成员 | 受C++成员析构管理；不会自动出现在QObject子树里 | 按职责保留提醒；隐藏呈现不订阅无关刷新；不凭树里没看到判断“没释放” |
| 同步Coordinator | AppRuntime unique_ptr；QNetworkAccessManager(this)，active为QPointer；完成reply.deleteLater，析构abort/代次失效 | 未见缺失reply释放的直接证据；本地模式也创建network/默认SSL配置 | 离线会话可评估惰性网络/TLS；大图/分块缓冲单列峰值，不能误指为小资料常驻原因 |
| 同步捕获/JSON | ACCOUNT写操作before/after图和回调缓冲；QByteArray/QJson隐式共享 | 可能在大资料下多代共存；复制表达式不等于立即全量深拷贝 | 限制并发持有代数，结束即释放；用同资料前/中/后测量，不改协议/鉴权来省RAM |
| 导入预览ImportPlan | TaskWorker.optional中保留QJsonObject；下一次preview或成功apply才reset | UI没有明确discard接口；load重建服务时未明确清此plan，缺少资料代次绑定 | 定义放弃/过期/切资料失效；仅做源码风险发现，尚未证明可跨资料写入，不宣称已有数据泄露 |
| 更新器 | 一份QProcess值成员；命令临时QProcess有finished/failed删除路径 | 对象常驻不等于子进程常驻；诊断模式禁用更新 | 正常安装版另测进程及缓冲峰值；结束后无额外常驻更新进程 |
| 托盘/原生菜单/日志 | 托盘QMenu/QAction有成员所有权，日志有轮换上限 | 本次隔离模式不创建真实托盘，不能伪称其已完成动态清点 | 保留恢复/退出通路；日志只留有界缓冲和脱敏字段 |

“未发现直接泄漏”仅是当前路径的静态判断。非QObject资源要用对应RAII/释放函数和实际分配证据检查，不能按这一张矩阵宣布全堆审计完成。

## 六、架构问题与改造优先级

### 1. 从“隐藏整树”改为“状态常驻、呈现按需”

业务/编辑事实由TaskWorkspace、EditorSession等持有；QML视觉树按使用周期创建。关闭视觉内容不清理业务事实，不用自动保存草稿来换低内存。密码不进入界面状态快照。

第一批明确不应冷启动常驻的内容：未使用日期/时间选择器、未编辑的完整详情/重复规则表单、非选中设置页、未打开独立日历/账号/数据工具的内容。逻辑控制器及原入口可以常驻，不能让“入口存在”要求“全部控件已创建”。

### 2. 去掉按任务行复制的菜单

TaskRow只报告任务身份、版本、作用域与锚点。宿主菜单在打开时捕获独立目标，不能绑当前选中行；保留右键另一行、取消、已删除/已修改版本检查。主窗和小窗各自有宿主，不能跨窗口错误复用锚点/透明度。已有小窗集中菜单可作为本仓库机制参考。

### 3. 按窗口而不只是按QObject管理图形生命周期

先验证低频窗销毁/资源释放后的真实变化；Qt释放接口是提示，分配器/驱动可能保留，不保证每次立即回落69MiB。若低频工具互斥，可评估共用一个辅助窗口宿主，但账号仍有独立入口/UI，不能挪进设置；设置和账号的模态/几何/焦点差异必须另做UX设计。

保留主窗＋小窗常用交互。关闭后的低频窗口不应无限积累独立图形上下文。basic render loop、设备共享、software或Widgets只作为后续有界对照，不直接切全局默认；必须同时检查输入延迟、首帧、菜单、透明、DPI与动效。

### 4. 避免用第二个“全局对象管理器”掩盖强引用

单纯在现有强持有树之外再加Registry，不会释放任何现有控件。真正的改变是解除创建关系、定义唯一拥有者和明确销毁时机；Registry只负责意图/实例代次和注册事件。

AppRuntime现在启动时findChild取独立日历并立即用minimumSize/挂WindowStateStore，不能直接套Loader造成空指针。按需实例必须在注册事件绑定状态存储；QPointer失效后取消旧请求。编辑中、菜单打开、拖动、IME、提醒、形态动效/待呈现帧都阻止回收，直到各自会话明确结束。

### 5. 临时数据应绑定会话/资料代次

ImportPlan等中间态有唯一owner、profileEpoch、创建时间和显式discard；切换资料前失效并释放。异步结果带request/instance/profile代次，失效不接到新对象。队列/缓存不只限条数，还应考虑持有字节和代数。失败态保留必要可重试信息，不保留整个已取消操作的文档。

## 七、从对象不变量重建验收

当前不再冻结220MiB或另猜一个RAM数字。先验证：

- 冷启动未使用选择器的重内容实例为0，打开后按宿主有界，关闭/无草稿后可销毁；字段值和焦点恢复正确。
- 未编辑会话不创建完整详情/时间/重复规则呈现；活动会话数量与UI实例一致。
- 任务数增加不再线性增加整套菜单；新增一行只增加行必需对象。
- 未使用低频窗口无内容/场景图，关闭并回稳后没有无上限图形资源保留；恢复延迟另行达标。
- 100轮预热后循环的对象、句柄、缓存容量及内存增长有界；本轮十次仅作初筛，不代替长测。
- profile切换不持有上一资料的导入文档/任务指针/晚回调；取消不修改数据库。

然后在同Qt/Release/图形API/显示DPR/资料/功能状态下重测必要常驻成本，再给产品预算。空窗89MiB不是完整软件承诺；200MiB也不是合理性豁免。

## 八、实施切片及测试责任

1. **OBJ-01 选择器和闲置编辑内容惰性化**：先只改一个DateField fallback路径，单测创建/关闭/重开、inline模式不建fallback、选择/取消/键盘/200%、共享宿主锚点；比较前后对象及私有提交，保留失败原记录。
2. **OBJ-02 主列表共享菜单**：TaskRow意图→宿主菜单，验证选中第二行右键第一行、软删/取消/版本变化、键盘与原生/回退菜单不透明及层级。
