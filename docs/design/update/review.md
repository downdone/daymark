# 方案评审记录

评审日期2026-11-05。结论：**主方案可行，完成下述设计修正后可以按切片开发**。无需新增服务端；不改用户提出的目录分离、后台安装、提醒重启和成功后删除旧版流程。以下是本轮单代理依据源码与官方API进行的静态评审，未虚构独立评审人或平台测试结果。

## 1. 保留的决策

1. 根启动器固定入口，实际程序按版本隔离，下载/旁路安装时旧版继续使用。
2. GitHub公开Release和资产API提供发现/下载；发布流程附加签名清单，最终资源齐全才就绪。
3. 更新器按需启动，Ready后退出；重启阶段重新启动完成切换。没有更新时不驻留、不安装Windows Service。
4. 重启仍经过草稿保存/命令排空；提交前失败可恢复旧版，新版正常运行后才删除旧程序。
5. 发布者签名、逐文件核验和受管路径约束；既有发布/许可/干净机门禁保持。

## 3. 安全与可靠性的实际边界

- 签名防未授权远端资源替换，不能防已经能任意改写同一用户程序/公钥的本机恶意代码。ACL和路径句柄约束处理误用/路径替换，不把当前用户可写目录描述为对同用户攻击者的完整安全边界。
- 原子替换一个状态文件不等于任意硬件掉电下全事务绝对原子。使用校验、备份提交记录和保守恢复；无法确定状态时停止切换，不猜目录。
- 同schema还需同读写ABI；提交前恢复只换程序，永不回填旧DB。首期不自动迁移数据，属于明确范围而非遗漏。
- 新版RUNNING且清理开始后旧版不再是回退资源。此后普通崩溃仍保留用户数据并提供修复入口，不承诺已经删除旧程序还能本地回退。
- GitHub被阻断/限流是更新不可用，不是应用不可用；网络失败不弹出登录错误，也不显示已最新。
