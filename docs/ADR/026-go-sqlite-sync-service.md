# ADR-026：可选登录同步与单体Go + SQLite服务

日期：2026-10-28。决策来源为用户在账号与同步设计评审中的明确指令。

## 已接受决策

1. 不登录账号时，Daymark使用本地存储，不执行账号同步；登录账号后，同步至服务器。
2. 服务端数据库体量和性能需求较低，首期采用单体Go + SQLite；后续有真实需求再升级。

本ADR只接受上述行为和技术方向，不把先前提案的PostgreSQL/Keycloak或全部认证/注册/隐私建议转成已接受需求。客户端继续固定Qt 6.10.2，已交付migration保持不改写。产品追踪见[FR-042](../01_PRODUCT_SPEC.md#fr-042-账号与存储模式2026-10-28用户确认)，详细设计见[账号与同步](../design/account-and-sync-service.md)。实施状态和验证证据只见[PROGRESS](../PROGRESS.md)。

## 对现有契约的解释

- 登录后仍先保存本地SQLite，再以持久化待传队列异步同步；断网不禁止编辑。登录不把任务CRUD变成网络必需操作。
- 登录即启用当前账号同步；首次登录按安全合并处理，过程可见，只有覆盖/清除及跨账号迁移等危险选择另行确认。
- 退出后停止同步并保留本地与待传数据；属于账号A的资料不自动上传到账号B，沿用本地优先、软删、备份和输入保护原则。
- 历史V1“默认不引入账号和服务器”保留为原阶段范围；本次明确需求允许设计其后续能力，不能借此推导已授权部署或传输私人数据。

## 采用SQLite的约束

首期单机、单Go实例、服务端同一个SQLite文件；账号/会话/业务/同步日志可同库事务，资料以owner和dataset ID隔离。WAL允许读写并行，但同一时刻只有一个写事务，不支持以共享网络磁盘让多个服务器直接写同一文件。[SQLite事务](https://sqlite.org/lang_transaction.html)、[WAL说明](https://sqlite.org/wal.html)。

设计使用串行写连接、短`BEGIN IMMEDIATE`事务、有限busy/请求超时、每连接外键校验及一致备份。服务器数据库是独立持久化，不能上传、覆盖或复用桌面私人SQLite文件作为服务器数据库。

数据库访问保持窄Repository/事务边界。出现实际写锁/时延问题、备份窗口过长或需要多个应用实例时，再评估PostgreSQL；不预先增加通用ORM、多数据库适配层或分库。迁移必须备份、暂停写入、核对实体/版本/删除及回执，协议游标必要时切换epoch，不以改连接串代替迁移。

## 依赖与待评审事项

Go内集成第一方账号/会话是符合单体方向的新建议，尚未由用户单独确认；首期不要求部署Keycloak。SQLite驱动候选为`modernc.org/sqlite`（BSD-3-Clause，无CGo），密码哈希候选为`golang.org/x/crypto/argon2`（BSD-3-Clause）。这两个候选尚未加入依赖；开始代码前另记录确切版本、引擎补丁、传递许可和平台验证，保留改选依据。

公开注册/账号恢复、端到端加密、冲突细节、提醒策略与具体部署环境继续按详细设计评审。本轮只修订方案，不标记服务端、登录或同步已实现。

用户后续要求工程化、易扩展及高可靠的详细架构，实施设计见[服务端工程架构](../design/server-architecture.md)及[v1协议草案](../api/sync-v1.md)。这两份细化文档不改变本ADR只接受账号/存储模式与Go+SQLite选型的范围；未验证的可靠性目标不是交付事实。

## 2026-10-29注册扩展

用户明确要求注册能力，实施可由运维开启的自助用户名/密码注册；旧配置默认关闭，示例显式开启。注册不绑定邮箱身份、不增加SMTP/邮件找回依赖；密码规则、通用应答、限流、重复请求和Qt交互见[实现契约](../design/sync-client-implementation.md)。既有管理员建号/重置仍可用，schema不变。
